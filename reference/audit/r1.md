## For DEVIATIONS.md

- Players: `CBasePlayer::Spawn` keeps the engine's FL_PROXY and FL_FAKECLIENT flags (the original
  sets pev->flags to FL_CLIENT), so HLTV proxies and bots stay marked as such.
- Messages: `UpdateClientData` sends halflife-updated's `Weapons` message (64-bit weapon bits) for
  today's client; the original has none.
- `fullupdate` (and impulse 204) run halflife-updated's fuller `ForceClientDllUpdate`, which also
  resets the HUD, FOV, weapon-bits, room-type and ammo caches and resends ResetHUD.
- If Steven keeps it: `CBasePlayer::TakeDamage` sends HLTV's SVC_DIRECTOR damage event, which the
  original doesn't.

## For ORIGINAL_BUGS.md

- `monsterstate.cpp CBaseMonster::RunAI`: tests SF_MONSTER_GAG (2) against pev->flags, which is
  FL_SWIM: a gagged monster still plays idle sounds, a swimming one never does. Kept (SDK 2.1's bug).

## Odd

- **Room type (needs r4, sound.cpp).** Our `CEnvSound` is still halflife-updated's: it stores the room
  type in `pPlayer->m_SndRoomtype` and `UpdateClientData` sends SVC_ROOMTYPE when it changes, and
  Spawn, Restore and ForceClientDllUpdate reset the client copy to -1, so the last room type is
  resent after every spawn. SDK 2.1's env_sound sends SVC_ROOMTYPE itself. Whichever way r4 goes,
  the player.cpp side (m_ClientSndRoomtype in Spawn and UpdateClientData) should follow; I left it.
- **ExtractAmmo order (needs r3, weapons.cpp).** Restoring the original's order means
  `CBasePlayerWeapon::AddToPlayer` calling ExtractAmmo again (SDK 2.1's AddWeapon) and
  AddPlayerItem dropping its own call. Safe now that GiveAmmo no longer gives the exhaustible
  weapon (that gift was why halflife-updated moved it).
- **sv_allow_autoaim.** `game.cpp` still fetches `g_psv_allow_autoaim`; nothing reads it now. On an
  engine without that cvar the old AutoaimDeflection crashed whenever sv_aim was non-zero.
- `CBasePlayer::m_iObserverLastMode` is set in UpdateClientData (halflife-updated) and read only by
  `observer.cpp`, halflife-updated's spectator code that RC's own observer doesn't use.
- `AmmoInfo::WeaponName` (weapons.h, weapons_shared.cpp) is now written and never read.
